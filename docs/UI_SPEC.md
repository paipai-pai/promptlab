# PromptLab UI 规范

## 1. 设计方向

PromptLab 采用“开发者工作台”风格：信息密度适中、结构清晰、操作可预期。界面应像长期使用的生产工具，而不是营销落地页或一次性演示。

设计关键词：克制、精确、可扫描、可信赖。正文编辑与实验数据是视觉重点，装饰不应压过内容。

## 2. 主题

- 同时支持浅色与深色主题。
- 使用 shadcn/ui 语义色变量，不在业务组件中散落硬编码主题色。
- 浅色主题使用低饱和中性色背景、清晰边框和深色正文。
- 深色主题避免纯黑大面积铺底，保持卡片、输入区和背景层级可辨。
- 系统偏好作为首次访问默认值；显式切换与持久化在 Phase 1 实现。
- 状态颜色只表达语义：成功、警告、错误、信息。

## 3. 页面布局

- 桌面端：左侧主导航、顶部上下文栏和主内容区。
- 移动端：主导航收起，主要操作保持可达。
- 主内容设合理最大宽度；编辑器与实验输出可使用更宽布局。
- 页面标题区统一包含标题、说明和主要操作。

推荐信息架构：Prompts 列表、Prompt 详情、Experiments、Account。Phase 1 只创建静态界面骨架，不接入真实数据或认证。

## 4. 组件规则

- 优先复用 `src/components/ui` 中的 shadcn/ui 原子组件。
- 业务组件放在对应 `src/features/<feature>/components`。
- 表单标签始终可见，错误信息紧邻字段并可被辅助技术关联。
- 主要操作每个页面最多一个；危险操作不得与主要操作同等强调。
- 对话框只用于需要聚焦或确认的短流程，不承载长表单。
- 表格用于可比较的结构化数据；窄屏改为卡片或允许有提示的横向滚动。
- 空态应说明当前为空的原因和下一步，而不是只显示插图。
- 图标必须服务于识别；单独使用时提供可访问名称。

## 5. Prompt 专用界面

### 5.1 Prompt 列表

- 显示名称、描述摘要、分类、最新版本号和更新时间。
- 支持清晰的空态与创建入口。
- 搜索、筛选、排序是否进入 MVP 需单独确认；Phase 1 可展示布局占位但不伪装为可用功能。

### 5.2 编辑区

- 名称、描述、分类与正文视觉上分组，明确元数据和版本化正文的差异。
- 正文使用等宽字体，保留换行，变量占位符可被识别但不改变原始文本。
- 显示“已保存”或“有未保存更改”状态。
- “保存元数据”和“保存为新版本”的文案及操作边界不可混淆。

### 5.3 版本历史

- 版本按时间倒序展示，显示版本号、创建时间和只读状态。
- 历史正文只读；如需基于旧版本继续编辑，应生成新的草稿，而非修改旧行。

### 5.4 实验记录

- 始终展示关联的 Prompt 名称与版本号。
- 输入快照、模型输出使用可复制的等宽内容区。
- 未保存草稿状态下，实验保存操作不可用，并解释原因。

## 6. 交互状态

每个数据界面至少设计首次加载、局部提交中、空数据、字段校验错误、权限或登录失效、服务端失败、保存成功和未保存草稿状态。

禁用操作必须同时提供原因；不能只依赖颜色表达状态。

## 7. 响应式与可访问性

- 以 360px 宽度作为移动端最低设计检查点。
- 键盘可完成导航、表单编辑、保存、预览和复制。
- 焦点样式清晰，不移除浏览器可见焦点而不提供替代。
- 正文与背景、控件与背景满足 WCAG 2.2 AA 对比度目标。
- 动效尊重 `prefers-reduced-motion`，且不承载唯一信息。
- 页面使用语义化标题层级、地标和表单标签。

## 8. 文案原则

- 使用明确动作：“保存元数据”“保存为新版本”“复制渲染结果”。
- 避免把未实现或不可用的功能包装成可点击操作。
- 错误文案说明发生了什么以及用户下一步可以做什么。
- 产品名使用 PromptLab，领域对象统一使用 Prompt、版本、实验。
